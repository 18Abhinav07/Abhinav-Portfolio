Stage 1 · measured on an M4 Pro, 24 GB, 120 Hz

Prefill makes the page stutter. Decode doesn't.

I reran the performance claims in DBR-2026-05 and DBR-2025-01 on a fifth machine. I also measured something neither paper does: how the browser feels while the model runs. When a local 7B model reads a 4,000-token page at llama.cpp's default batch size, a GPU-heavy page drops most of its frames for the whole 11 seconds. A 64-token batch fixes that for about 10% more time to first token. That fix doesn't carry over to 14B, and the data suggests it won't carry over to smaller Macs either.

What the data says

Five findings

01 · Prefill, on GPU-heavy pages

Third-party pages stutter. Text pages don't.

Every page idles at 0% dropped with no model loaded. At the default batch, 7B prefill drops 83% of frames on WebGL Aquarium, 64% on the shader page and 30% on MotionMark Arcs. It drops 0% on BBC News and on a light page. Decode drops nothing on any GPU-heavy page.

02 · The cause is the GPU

Size of each GPU submission matters. Pauses don't.

CPU-only prefill keeps the shader page smooth (0.1%) but takes 104 s instead of 11.5 s. Pausing 16 or 50 ms between 128-token chunks still drops 34 to 38%. 64-token chunks are smooth with no pause at all. What matters is how long each GPU kernel holds the GPU, not whether the queue has gaps.

03 · The fix moves with the model

Batch 64 fixes 3B and 7B. It doesn't fix 14B.

On the shader page batch 64 takes 3B from 69% to 0% and 7B from 64% to 1.3%. 14B still drops 31% at 64. A fixed value safe for 14B (32 or less) costs 7B about 17% TTFT on every page, including pages that never needed it.

04 · A second engine agrees

Safari shows the same pattern at 60 Hz.

Safari drops 14.5% during 7B prefill on the shader page (p95 32 ms against a 17 ms budget). Decode drops 0%, and batch 64 brings it to 0% for 6% more TTFT. At 60 Hz each frame has twice the time budget, so the same GPU stalls miss fewer deadlines.

05 · CPU is a second resource

Falling back to the CPU is worse, not safer.

On MotionMark Multiply, a CPU-bound page, GPU inference drops 6 to 10%. CPU inference drops 22% in prefill and 30% in decode, and four threads still drops 18%. Anything that runs on CPU cores needs its own budget, which matches DBT-2026-09's 12%-of-a-core cap on background embedding.

And the paper's limits

Cold TTFT is 11 s, not 640 ms.

7B at 4k tokens takes 11.4 s cold and 79 ms when the page is already in the KV cache, so the 640 ms figure only fits a cached prefix. No model gets a cold 4k prefill under 900 ms here. Decode and memory pass easily. 24 GB shows no swap cliff, and Q8 prefills faster than Q2_K.

Why it matters

“A model that starves the compositor produces a janky browser, which testers blamed on the browser rather than the model.”DBR-2026-05

Running models on the user's own machine only works if the browser still feels fast while they run. This is that failure measured, narrowed down to one phase, and given a cheap first fix.

The fix isn't the whole answer. It holds for 3B and 7B on this machine, and the 14B run suggests a base M1 or M2 behaves like this machine running a bigger model. The next step starts with the fix and builds only as much scheduler as the slower machines need.

Method

How it was measured

Inference. Qwen 2.5 Instruct GGUF (bartowski quants) on llama-server, all layers on the Metal GPU unless noted. Every E4 trial prefills a fresh 4,000-token page with the prompt cache off, then decodes 256 tokens.

Frames. Brave opens its own profile and a calibrated page, which idles at 120 fps with no model loaded. A recorder injected over DevTools logs every requestAnimationFrame interval and every long animation frame. The harness marks idle, prefill, decode and gap phases on the same clock.

Dropped frame. A frame whose interval is more than 1.5× the page's own idle median. Each condition gets 5 measured trials after a warm-up. Conditions run in an interleaved order, and the machine stays on AC with nobody touching it.

Pages: a light page (WebGL + scroll), the shader page (raymarch + scroll), WebGL Aquarium with 20,000 fish, MotionMark CanvasArcs (complexity 10,000) and Multiply (2,000), BBC News scrolling, and Safari on the light and shader pages.

With 24 GB, 18 GB of other memory slows 7B decode by 6%. Swapping starts between 8 and 14 GB of ballast, and the 2.3× cliff the paper describes never appears.

The decision rule, and its amendment

Verdict: scheduler

The rule I fixed before E4 read only the light page, and on that page it said “build the capability gate” (). After the shader page showed 64% drops, I changed it so the worst page decides. Both verdicts are printed in the report.

Limits, read before trusting the numbers
  • One machine. Brave stands in for Dart (both Chromium), and Safari is the second engine at 60 Hz.
  • Qwen 2.5 on llama.cpp 0.7.0, while Dart used b4021.
  • rAF intervals track page rendering, not compositor presentation.
  • Not run: accuracy (it needs Dart's 640-item set), speculative decoding (E3; only an invalid battery preview exists), thermal sustain (E5) and energy (E6, which needs root for powermetrics).
  • One 4-minute condition ran while something outside the benchmark halved decode speed. It is kept, labelled “disturbed”, and was rerun.

What I'd do next

Ship the fix now. Build the scheduler only as far as small Macs need.

Stage 1 found a cheap fix that works on this machine. It also found evidence that the fix stops working as the GPU gets slower relative to the model. The plan below is in that order: ship the fix, test the small-Mac prediction, and add machinery only when a measurement says the simpler step failed.

Step 1
This week

The immediate fix: prefill in 64-token batches

Set n_ubatch = 64 for 3B and 7B. On the M4 Pro this takes every GPU-heavy page to about 0% dropped. It costs 9 to 11% TTFT on heavy pages and about 5% on pages that were already smooth. 14B needs 32 or less.

Decode is left alone. It never dropped frames on a GPU-heavy page at any setting.

Step 2
The thesis

Why 64 probably fails on a base M1 or M2

Batch 64 works on the M4 Pro because each GPU kernel finishes quickly enough for the page to get the GPU back in time. A 7B batch-64 step there takes about 200 ms in total (4,000 tokens in 12.8 s at 64 per step), and the page still stays smooth. So the total length of a step isn't what matters. The length of each kernel inside it is, and that scales with tokens per batch times model width, divided by GPU speed.

14B prefills 2.07× slower than 7B on this machine (23.7 s vs 11.4 s cold at 4k). That is the same ratio as the M4 Pro to a base M2 with 10 GPU cores in llama.cpp's own Apple Silicon numbers. So 14B on the M4 Pro is a stand-in for 7B on a base M2 or M3, and at batch 64 it still drops 31%.

7B Q4_0 prompt processing (pp512), from the llama.cpp Apple Silicon benchmark thread (ggml-org/llama.cpp discussion #4167). The prediction is what I'd expect for 7B Q4_K_M from the proxy ratio. It hasn't been measured.

Two effects pull in opposite directions, so treat this as a prediction to test. Base MacBook Airs have 60 Hz displays, which gives twice the frame budget (Safari at 60 Hz dropped 14.5% where Brave at 120 Hz dropped 64%). A smaller GPU also renders the page itself more slowly, which leaves less headroom. ./reproduce.sh settles it on a real Air in 15 minutes.

Small fixed values cost a lot more on slow machines. Batch 32 already costs 7B 17% TTFT on the M4 Pro. A cold 4k prefill on an M1 takes 35 to 40 s before any penalty, so a constant small enough for the slowest machine taxes every other machine all the time.

Step 3
Weeks 2 to 4

A per-device, per-model table, plus a mode switch

  • Table. The largest safe batch for each chip class and model, measured by this harness. On this M4 Pro that is 64 for 3B and 7B and ≤32 for 14B. For unknown chips, start from a feedforward estimate: time one batch at startup, then divide a per-kernel time budget by the measured per-token cost.
  • Mode switch. Use the small batch only while a GPU-heavy page is in front, and the full batch (up to 1,024; 2,048 drops 2.9% even on the light page) when the window is hidden or the page is light. BBC News and the light page then stop paying the 5% for nothing.
  • The knob. In-process, the caller hands llama_decode k tokens per call, so k can change every step with no reload. llama-server can't do this, because ubatch is fixed at load. My HTTP version (one request per chunk) costs +23% at 64 tokens, against +11% for ubatch 64. The first measurement is whether in-process chunking closes that gap.
Step 4
Only if needed

An adaptive controller, with a stop rule

If a table entry still drops frames on real pages, add feedback: read missed deadlines for the frontmost tab in 250 ms windows, halve k when drops rise above the page's idle rate, and grow it back additively while frames stay clean. The table gives the floor and ceiling.

Stop rule: if the table alone is safe on a base M1 for less than 10% extra TTFT, ship the table and don't build the controller.

Step 5
Same signal

Everything else that competes with the frame

  • Speculative decoding. Verify batches of 4 to 16 tokens are well under the safe size, so I predict they're safe. That's worth checking, because Dart's agenda lists “speculative decoding schedules that yield to the compositor under load” as open.
  • Background embedding. Index maintenance that “never competes with rendering” gets the same frame signal. DBT-2026-09 caps it at 12% of a core.
  • A CPU thread budget. CPU fallback is worse than the GPU problem (22 to 30% drops on a CPU-bound page). Any CPU-side work gets a thread budget instead of llama.cpp's default of every performance core.
  • Alternative to compare against: prefill on the Neural Engine, which doesn't share the GPU at all, if the model and tooling allow it.
Done when

Success criteria, fixed before building

Smooth
On every GPU-heavy page, prefill drops at most 2 points more than idle, for 3B, 7B and 14B, on the M4 Pro and on a base M-series Air.
Free
On light pages, TTFT within 2% of batch 512.
Cheap
On heavy pages, TTFT no worse than the smallest fixed batch that is smooth for that model and machine.
Fast
When a heavy page comes to the front mid-prefill, drops recover within 500 ms.
Honest
If in-process chunking costs as much as the HTTP version, the report says so, and the design switches between two or three preloaded contexts instead.
Deliverables
  • The batch-64 change, with this harness as its regression test.
  • The device/model table, measured on at least two Macs, one of them a base M-series Air.
  • dartsched, a small C++ layer over llama.cpp: chunked prefill through llama_decode, the mode switch, a pluggable frame signal, and the controller only if step 4 is triggered.
  • A frame-signal prototype built on the rAF recorder this harness already injects. The production hook belongs in the browser's compositor.
  • A report comparing batch 512, fixed 64, the table and (if built) the controller.
